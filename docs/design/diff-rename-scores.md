# Shared diff rename and copy scores

`diff_opt_find_renames`, `diff_opt_find_copies`, and `diff_opt_break_rewrites` all call `diff.c:parse_rename_score` in the inspected Git 2.25.1 and 2.55.0 sources. A score accepts zero or more ASCII digits, an optional dot and more digits, and an optional terminal percent. Empty strings, a bare dot, a bare percent, and dot-percent are accepted. Break rewrites additionally accepts at most one slash separating two such fields; either field may be empty. Signs, whitespace, exponent/hex notation, repeated dots/percents, and unconsumed suffixes are invalid. Values need not lie between zero and one hundred.

The registry validates lexical acceptance only. It does not calculate or normalize native similarity scores, clamping, unsigned-long arithmetic, object matching or later rendering. Raw supplied strings and emitted argv remain unchanged. Internal `true` represents a bare optional argument and is accepted by these profiles; a supplied boolean still fails the public string shape.

Bindings follow the evaluated native callback function, including the short aliases and retained parser tables. This preserves the distinct `-M/-C` meanings in the blame, annotate and pickaxe frontends, whose final option tables shadow common diff options. Long find-renames/find-copies options retain the common callbacks. Existing continuing, streaming, initial help and difftool final tool-help phases remain in force. Earlier callback errors cannot be erased by later occurrences or disabling flags. Unknown repository-dependent stash gates remain native-owned.

Runtime validation consumes the complete value rather than relying on a JavaScript dollar anchor that can match before a final newline. Literal validation uses the existing dynamic/budget policy after rejecting guaranteed malformed ASCII and punctuation; it does not promise complete analysis of arbitrary symbolic or compiler-budget-exceeding text. Dynamic strings are validated at runtime. Global NUL and ignored-tail shape checks remain separate.

The baseline pilot compares 6,960 native/public help invocations across Git 2.25/2.47/2.55/2.56, five representative commands, six spellings, 29 values and both help orders. Those invocations agree at runtime; the missing feature is literal/preflight grammar validation, not a claimed existing runtime compatibility bug. Earlier empty-short-alias pilot controls and the initial pickaxe-shadow fixture failure are preserved with corrected evidence. Later tests and type proofs must be qualified by their actual head and scope. Finite help controls do not establish rename/copy payload semantics or complete command auditing.

The command type evaluator caches the finite rule-key projection per command. Option-table and numeric-option key calculations retain their original handling of command-name unions and `never`. This avoids repeating the rule traversal for individual invocation states without changing accepted argument shapes. Focused diagnostics can measure this reduction; the complete contract suite remains a separate unchanged-heap gate.

Argument vocabulary tuples are shared by flag spelling, value kind and accepted value type, rather than by the complete option metadata. The kind checks remain non-distributive, preserving mixed-definition unions and optional arities. This is a type-evaluation change only; native callback selection, serialization and runtime validation are unchanged. Complete contract validation remains required independently of focused measurements.
